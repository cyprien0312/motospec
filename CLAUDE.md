# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

MotoSPEC Formula Explorer — a static, single-page motorcycle chassis geometry calculator served as plain ES modules over HTTP (no bundler, no build step). The app explores parameter chains for trail/rake, computes 4-bar linkage kinematics, and renders motion-ratio / progression curves. Bilingual UI (zh / en).

## Commands

- Run tests: `npm test` (Node's built-in runner via bare `node --test`; Node 22+. Do not write `node --test tests/` — newer Node 22 rejects a bare directory argument; default discovery finds `tests/**/*.test.js`).
- Run a single test file: `node --test tests/linkage.test.js`
- Run a single test by name: `node --test --test-name-pattern='pro-link' tests/linkage.test.js`
- Local dev server: already running as a systemd user service — `motospec-dev` serves the repo root at `:5173` (`systemctl --user status motospec-dev`; LAN `http://192.168.1.153:5173`). Plain static serving; edit a file, refresh the browser. `index.html` imports modules from `./src/` so the app must be served over HTTP, not opened via `file://`.

There is no lint, no build, no bundler. Don't introduce one without asking.

- **`scan/` — 3D scan → chassis/linkage data pipeline** (Python, entirely separate from the app; the JS side has no build step and gains none from this). Point cloud → `batch_fit.py` (fits cylinders, builds the bike frame, emits hardpoints) → `motospec_export.py` (translates to OUR field names + cross-checks) → catalog entries. `chassis_geom.py` / `batch_fit.py` / `config.example.json` / `SCAN_WORKFLOW.md` came from outside and their numeric path is **unmodified**; `synth_scan.py` (synthetic ground-truth generator) and `motospec_export.py` are ours. Validated end to end against synthetic data: rake 0.002°, wheelbase 0.00 mm, hardpoints < 0.05 mm, and the exported entries reproduce the truth through `computeAll`. `scan/README.md` is the step-by-step operator guide (Chinese). Env: `scan/.venv` (numpy + scipy; gitignored, rebuild with `python3 -m venv .venv` + `~/.local/bin/pip --python .venv/bin/python install numpy scipy`). **This is the only route to the 10 linkage coordinates** — see `docs/research/linkage-coords.md` for why they cannot be sourced any other way.

- **Windows exe**: `MotoSPEC.exe` at the repo root is a self-contained double-click launcher (embedded copies of `index.html` + `src/*.js` + `data/*.json`, minimal loopback HTTP server, opens the default browser). Rebuild it with `powershell -ExecutionPolicy Bypass -File windows-launcher\build.ps1` (uses the csc.exe that ships with Windows — no SDK) **whenever `index.html`, `src/`, or `data/` change**, or the exe serves stale files. Source: `windows-launcher/MotoSpecLauncher.cs`.

## Architecture

### Module layout (ES modules, no bundler)

- `index.html` — the entire UI shell, styles, and DOM wiring. Imports from `./src/*.js` at the top of an inline `<script type="module">`. Because handlers are referenced from inline `onclick` attributes, the module **deliberately re-exposes them via `Object.assign(window, {...})`**. When you add a new inline-handler function, it must be added to that window assignment or the button silently does nothing.
- `src/formulas.js` — pure parameter graph. `P` is the registry of every channel/intermediate node with `formula`, `deps`, units, descriptions. `INPUT_META` declares every leaf input (defaults, min/max/step). `CALC` maps node names → pure compute functions. `TOPO_ORDER` is the topological evaluation order. `defaultValues()` and `computeAll(inputs)` are the public entry points. **No DOM, no i18n, no side effects** — keep it that way; tests import it directly. Note on `INPUT_META.step`: for the **live setup keys** it is the real-world *adjustment* increment lifted from real MotoSPEC's PageUp/PageDown table (Yoke_Offset 1, Rear_Spring_Rate 2.5, Rear_Topout_Rate 10, oil level 5 …) — one spinner click should equal one thing you'd actually do at the track. The `*_ref` baselines keep finer steps: a ref is *measured*, not dialled. `tests/stroke-and-limits.test.js` pins both.
- `src/linkage.js` — 4-bar linkage closure kernel. Reference frame: origin at swingarm pivot, +X forward, +Y up, mm. Newton-Raphson closure in `closeFourBar`. Three `Linkage_Mode` values: `'linked'` (rocker on frame, e.g. R7 / RS660 / Unitrack) and `'pro-link'` (rocker rides the swingarm; Honda family) share one 4-bar solver, while `'linkless'` (Direct / Linkless — R3, KTM 890/990 Duke) bypasses the closure entirely: `shockLowerEnd` just rotates the swingarm-side mount about the pivot, so it can never fail to converge. Linkless reuses `Drag_To_Swingarm_*` as the shock's swingarm mount and `Frame_Shock_Top_*` as the frame mount; the six rocker coords are carried but never read (mode switching stays lossless). Its progression comes out near zero — the honest answer for a linkless rear end, pinned by `tests/linkless.test.js`. Pro-Link is implemented as the linked closure with β negated — working in the swingarm's rotating frame. `shockLength` likewise transforms the shock-top point into the swingarm frame in pro-link mode. Don't fork the solver; preserve this trick. **Honesty guards:** an unconverged closure (|residual| ≥ 1e-6) poisons `rockerShockEnd`/`shockLength` to NaN, and `swingarmDeltaForShockTravel` scans for a finite sign-change bracket before bisecting (the mechanism can lock inside ±45°) and returns NaN when the target is unreachable. Never re-introduce endpoint/unconverged fallbacks — a NaN renders as an honest "—" in the table; a fake finite number doesn't.
- `src/linkage-setup.js` — render function for the Linkage Setup page (SVG topology, input cards, motion-ratio chart, two input styles: Cartesian XY vs. lengths-only). The lengths-only mode keeps 3 fixed XY anchors (rocker pivot, drag anchor, frame shock top) and 4 measured lengths; geometry is solved by chained two-circle intersections (`circleCircleIntersect`) with branch selection via `pickNearestBranch` (closest to previous solution).
- `src/chassis-setup.js` — render function for the Chassis Setup page. Frame geometry, mass + CG, aero share, tire — all chassis-side inputs that aren't linkage coords or component specs. Auto-fits a traced sport-bike side-view SVG to the user's `WB` and `Rf`; `CHASSIS_GROUPS` defines the field grouping, `CHASSIS_SPEC_FIELDS` the round-trip set saved to / loaded from the chassis catalog. **`CHASSIS_ENUM_FIELDS`** is a parallel, *non-numeric* set (`Fork_Position_Ref_Type` / `Swingarm_Length_Ref_Type` / `Rear_RH_Ref_Type`) recording **how** a setup number was measured — real MotoSPEC's Reference selectors. They are metadata: deliberately NOT in `CHASSIS_SPEC_FIELDS` / `CHASSIS_PROVIDED` (so they can never gate a RESULTS cell), no `INPUT_META` entry, no `P` node, no formula reads them. Default is `''` = "not recorded" — stamping an unstated convention on someone's number is the same class of error as inventing the number, so an unset convention stays *absent* from the saved profile. Each declares `implemented:` (the one convention the geometry chain actually assumes); `chassisEnumIsUnmodelled()` drives a "not modelled" badge when the recorded convention differs. Rendered by the `kind: 'enum'` group via `setChassisEnum` (not `setChassisInput`); persisted through the `k in merged` guard in `loadState` by an explicit `CHASSIS_ENUM_KEYS` pass. Linked pairs (`front_weight_dist`↔`rear_weight_dist`, `C_f_aero`↔`C_r_aero`) auto-mirror in the `setChassisInput` handler. `Yoke_Offset` and `Fork_Position` belong to the chassis profile (per-bike setup numbers, not fork-side specs). The page shows **one input per setup quantity** — the `*_ref` baseline fields (`Fork_Position_ref` / `Shock_Length_ref` / `Swingarm_Length_ref` / `Yoke_Offset_ref`, the setup at which `Rake_Static` and `WB` were measured); the live setup keys are not rendered and mirror the refs via `SETUP_MIRROR` (on edit in `setChassisInput`, and enforced again in `buildChassisPresetEntry` on save), so a loaded profile always starts at zero delta — "what the bike currently runs" is expressed as a per-column Data Table override (`SETUP_OVERRIDABLE`), never in the shared profile. the sag load case computes attitude/wheelbase deltas against them, so `WB` is a one-time reference measurement, never hand-edited for setup changes (chain-adjuster moves go through `Swingarm_Length`, offset swaps through `Yoke_Offset`). Fork swaps enter as `Fork_Length_Delta` (typed measured difference, ALWAYS_READY, 0 = same fork) because no fork's absolute length is known — absolute `Fork_Length` exists as an input but is deliberately unconsumed (zero-fake-data). Tire swaps follow the same pattern: `Rf` is the BASELINE tire's loaded radius (part of the trail identity it was derived from — never edited for a tire change); `Tire_Rf_Delta` / `Tire_Rr_Delta` (typed differences, ALWAYS_READY, 0 = same tire) feed the pitch chain vertically, and the front delta also enters the trail formulas' effective radius (Rf + Δ).
- `src/data-table.js` — reference-bike comparison table. `ROW_GROUPS` is the section list (FRAME GEOMETRY — just the chassis selector, FRONT/REAR SETTINGS, LOAD CASE — the two sag inputs, SPROCKETS, RESULTS). RESULTS is a single **live** block computed at the current load state: `Sag_Front`/`Sag_Rear` (both `ALWAYS_READY`, 0 = genuinely unloaded) drive `Pitch_Sag` and the delta chain in `formulas.js`, so rake/trail/swingarm-angle/motion-ratio/`Wheelbase_Live` all respond to sag and to fork/shock geometry deltas; at zero sag and zero deltas every value degenerates exactly to static (pinned by `tests/sag.test.js`). Ported from real MotoSPEC (`docs/research/motospec-v5-teardown.md`): `Spring_Center` (rear ÷ (front+rear) wheel rate), `Wheelie_Limit` / `Braking_Limit` (g; the WB cancels out of the wheelie one — CG movement with compression is deliberately unmodelled because we hold the CG in ground, not frame, coordinates), and the LOAD CASE pair `Front_Stroke_Pct` / `Rear_Stroke_Pct` — both **component-level** so front and rear are comparable where the raw sag millimetres are not; the rear one goes through `Shock_Travel_Live` (two 4-bar `shockLength` solves) rather than the wheel-travel ÷ motion-ratio shortcut, pinned by `tests/stroke-and-limits.test.js`. `Fork_Stroke` is the fork-catalog counterpart of `Shock_Stroke` (real 115 mm on both Showa BPF 765 entries, from the race-support sheet). Three RESULTS rows carry a **display mode** (`RESULT_MODES` in `data-table.js`): Anti-Squat (`Anti_Squat` / `Anti_Squat_Delta` / the `AntiSquat_Angle`+`Load_Transfer_Angle` pair / `AntiSquat_Angle_Delta`), Motion Ratio (`Motion_Ratio` vs `Motion_Ratio_Shock_Wheel`) and Progression (`Progression` vs `Progression_Wheel100`). These are presentation only — same physics, different conventional reading — but comparing two sources across different modes is the most common false discrepancy, so the mode is shown in the row label along with its unit. `Load_Transfer_Angle` exposes `theta_cg`; its definition is still **open** (their manual describes the load-transfer line from CG height and WHEELBASE, we use CG-to-rear-axle) and the oracle screenshots can't settle it because none of them show a CofG. Bike columns are variable (0…`MAX_BIKES`=5) — added/removed via `addBike` / `removeBike`. `defaultBikes` seeds three blank columns from `REFERENCE_BIKES`; `blankBike(idx)` mints fresh ones. Readiness follows the calculation **actually taken**, not the worst-case dep graph: a `P` node may declare `skipDepsWhen: {requires, test, deps}` naming deps that drop out under a stated condition, and `leafInputsFor(id, values, ready)` honours it. `swingarm_delta_solve` uses this — zero shock delta short-circuits to 0 before any linkage coordinate is read, so a complete chassis profile computes rake/trail/wheelbase with **no linkage profile at all**. The honesty rule: the condition may only be trusted when the keys it READS are themselves bound, because an unbound key still holds its `INPUT_META` default and a default proves nothing. `tests/conditional-readiness.test.js` pins the rule against the real solver (strip the coords, confirm the answer is still exactly 0). `bikeReadyKeys(bike)` is the source of truth for which inputs are "really bound" (chassis profile + selected components + per-cell user overrides + `ALWAYS_READY`); RESULTS cells whose leaves aren't all bound render blank with a "Need: …" hint built by `summarizeMissing` + `buildProviderMap`. `CHASSIS_PROVIDED` / `LINKAGE_PROVIDED` enumerate which inputs the chassis / linkage definition domains contribute (kept in sync with `CHASSIS_SPEC_FIELDS` in `chassis-setup.js` and `LINKAGE_COORD_FIELDS` in `linkage-setup.js` — `tests/domains.test.js` asserts the sync, pairwise domain disjointness, and single-provider coverage of every RESULTS leaf; keep it green when touching any of the four lists). Rendering computes from `effectiveBikeValues(bike)` — a fresh defaults→chassis→components→sprockets→overrides materialization from the **live** `CATALOGS` on every render — never from `bike.values`, which is only a legacy copy taken at selection time (catalog edits must reflow into columns without reselecting). Chassis-domain input rows render as **read-only echoes** of the selected chassis profile (blank + "Need: Chassis profile" hint when none); chassis keys in `bike.overrides` are deliberately ignored for both readiness and compute — the Chassis Setup page is the only place chassis values are defined — **except** the three `SETUP_OVERRIDABLE` keys (`Yoke_Offset`, `Fork_Position`, `Swingarm_Length`): these are per-column adjustable setup numbers that render as editable inputs once a chassis profile is bound (never before — the delta chain needs the profile's `*_ref` baseline), apply as overrides layered on the profile in `effectiveBikeValues`, and get an amber `dt-input-override` accent when diverging from the profile value. They still never create readiness on their own. The `MASS_OVERRIDABLE` keys (`Mass`, `H_CG`, `L_CG`, `front_weight_dist` — the MASS & CG row group) are looser: no `*_ref` coupling, so they render as always-editable inputs, overrides DO create readiness and feed compute even without a chassis profile, and typing the front weight share auto-derives `rear_weight_dist = 1 − front`. Rows can also carry `enum: '<CHASSIS_ENUM_FIELDS key>'` — a read-only echo of the selected chassis profile's measurement convention (blank + "Need: Chassis profile" with none bound; `—` + "not recorded" tooltip when the profile records none). This is the one place `data-table.js` imports from `chassis-setup.js` (`chassisEnumLabel` / `chassisEnumIsUnmodelled`): conventions are strings outside every numeric definition domain, so there is no duplication contract to uphold and one source for the option labels is correct. **HIGHLITE** (`state.dtHighlite`, an index or null) marks cells that differ from a reference column with `.dt-diff` — **settings and component selections only, never RESULTS** (results are the consequence; the settings are what changed), matching real MotoSPEC. `patchDataTableView` in `index.html` syncs `td.className` for *every* cell (not just `.dt-readonly`) so the diff class follows a value being typed without replacing the focused `<input>`. **`COPY_SCOPES` + `applyCopyScope(dest, src, scope)`** implement MotoSPEC's "copy Front / Rear / All settings from another column"; scopes are lists of `ROW_GROUPS` headers so new settings rows are covered automatically (`tests/highlite-copy.test.js` asserts every non-RESULTS group is reachable from `all`). Copy moves only what the source actually *set* and **clears** what it didn't — a leftover value masquerading as freshly copied is the failure mode being designed out. `COMPONENT_TO_CATALOG` is exported and is the canonical map — `index.html` imports it; do not redefine locally. Rows can carry a `status` badge (`pending` for inputs not yet consumed by any RESULTS; the `static` badge was retired with the sag load case — no RESULTS row echoes an input anymore) — corresponding CSS classes live in `index.html` (`.dt-status-*`). The "this row needs real linkage coords" badge was retired once `bikeReadyKeys` started blanking those cells with a "Need: Linkage coords" hint instead.
- `src/cg-calculator.js` — centre-of-gravity calculator rendered as a section on the Chassis Setup page (not a route of its own — it writes into `H_CG` / `L_CG`, which live there). `solveCG(rows, {wheelbase, axleHeight})` is pure and unit-tested against synthetic readings generated from a known CG. LEVEL rows fix the horizontal position, RAISED rows each yield one height estimate via `h = ΔW·L / (W·tanθ)` (height above the AXLE LINE; `+ axleHeight` gives H_CG). Anything not honestly derivable comes back `null` with a warning code rather than a partial guess, and nothing reaches `state.values` until the user presses Apply. The scale readings live in `state.cgRows`, deliberately NOT on the chassis profile: they are a measurement session, the profile carries the result. `patchChassisView` swaps only the calculator's read-only parts (`.cg-readout-strip`, `.cg-warnings`, `td.cg-derived`) so typing never loses focus.
- `src/reference-bikes.js` — three neutral placeholder columns (`Bike A/B/C`) that `defaultBikes` seeds from. The previous Yamaha R7 / Suzuki GSX-8R / Aprilia RS 660 mockup was removed because its geometry was never accurate enough to validate against. To populate a column: pick a chassis profile + components from the catalogs, or type values into the table cells. `tests/fixtures/reference-bikes.json` is a separate validation harness that pins published spec-sheet numbers (Trail / Wheel Rate) against real bikes (R6, CBR1000RR, Panigale V4) — kept independent of the Data Table seeds. `COMMON_ENV` carries env defaults (`a_x`, `V`, `Cd`, `C_f_aero`, `C_r_aero`) materialized into each bike via `materializeBikeInputs`.
- `src/catalog.js` — component catalog system. `CATALOGS` = base layer ⊕ user overlay (localStorage), where the base layer is the **shared Supabase library** once it loads (`applyRemoteCatalogs`), falling back to the bundled baseline JSON (`data/*.json`) before the fetch resolves / offline. Public API: `setCatalogEntry`, `patchCatalogEntry`, `removeCatalogEntry` (tombstones baseline), `getUserOverlay` / `applyUserOverlay` / `resetUserOverlay` / `clearLocalOverlayEntry`, remote-layer fns `applyRemoteCatalogs` / `setRemoteEntry` / `removeRemoteEntry` / `getRemoteCatalogs` / `hasRemoteCatalogs`, `materializeBikeInputs(bike)` which merges `COMMON_ENV` + selected catalog entries → flat input dict. Four catalog keys: chassis, forks, shocks, linkages.
- **Shared component library (Supabase).** `src/supabase.js` is a dependency-free PostgREST client (plain `fetch`) against project `tlakhfplzjdtptodocbv` (org `aim2motec`), table `public.motospec_components` (`catalog`, `entry_id`, `data jsonb`, `deleted`, `author`, timestamps; unique `(catalog, entry_id)`). Community-editable model: anon may **read/insert/update but never hard-delete** (RLS; removals flip `deleted=true`); every write is appended to `motospec_components_history` by a SECURITY DEFINER trigger, so any change is reversible. The publishable/anon key in `supabase.js` is public by design — RLS is the boundary. `index.html` loads it at startup (`initSharedCatalogs`, cached to `localStorage['motospec_shared_catalogs_v1']` for instant/offline load) and every catalog/chassis/linkage save pushes to the shared table (`pushEntryToShared` / `bulkUpsertShared`), then serves it from the remote layer. `publishLocalToShared()` migrates a browser's legacy local overlay up. Pre-migration baseline snapshot: `backups/catalog-snapshot-2026-07-22.json` + git tag `catalog-pre-supabase-2026-07-22`. Manage the DB via the Supabase MCP (migrations/SQL); restore from history or the backup snapshot. The clamp and swingarm catalogs were removed in v0.1.x because their only specs (`Yoke_Offset` and `Swingarm_Length`) were already chassis-profile fields — having them in two places caused silent overrides during `materializeBikeInputs`. Both fields now live on the chassis profile only. The `chassis` baseline (`data/chassis.json`) starts empty — chassis profiles saved from the Chassis Setup page populate it. Linkage profiles saved from the Linkage Setup page (`buildLinkagePresetEntry` + `slugifyLinkageName` in `src/linkage-setup.js`) round-trip through this catalog. `materializeBikeInputs` flattens chassis specs first so per-bike geometry and component-level specs can override.
- `src/user-guide.js` — bilingual long-form help page rendered at the `__guide` sentinel route. `GUIDE_ANCHORS` enumerates the section ids (`getting-started`, `dashboard`, `chassis`, `linkage`, `datatable`, `catalogs`, `concepts`, `faq`); `renderUserGuide({ lang, anchor })` returns an HTML fragment with `<section id="guide-…">` blocks. The host (`index.html`) drives a fixed `?` button (`.help-fab`) that calls `openGuideForCurrentPage()` → maps `stack[last]` via `PAGE_TO_GUIDE_ANCHOR` → `openGuide(anchor)` which sets `state.guideAnchor` and `navigateRoot('__guide')`. `state.guideAnchor` is one-shot (cleared after the post-render `scrollIntoView`) and intentionally not persisted to localStorage. Drill-down parameter pages fall through to the `dashboard` section. When you add a new top-level page, also add it to `PAGE_TO_GUIDE_ANCHOR` and write a matching guide section.
- `data/*.json` — baseline catalog entries (`forks.json`, `shocks.json`, `linkages.json`, `chassis.json`), loaded via JSON Import Attributes (`import X from '../data/x.json' with { type: 'json' }`). Requires Node 22+; TS LSP needs `jsconfig.json` (`module: ESNext`, `moduleResolution: Bundler`, `resolveJsonModule: true`) to avoid false-positive diagnostics on the `with` syntax. Don't downgrade to fetch/`require` — keep the native import. `chassis.json` ships empty; populated via the Chassis Setup page.

### State + render model in `index.html`

- A single `state` object (values, lang, current page). `renderContent()` re-renders the active page by replacing `#content.innerHTML`. This destroys focus, so:
- **`patchLinkageView()` does a scoped DOM swap** of just `.linkage-svg`, `.linkage-readout-strip`, and `.linkage-chart-wrap` to preserve focus while typing in input fields. When you add new live-updating regions to the linkage page, either include them in the patch or accept that they'll only refresh on a full re-render.
- Bilingual strings live in parallel `UI.zh` / `UI.en` tables inside the renderers; lang is part of `state` and toggled by a button.

### Linkage modes — placeholders and defaults

- Default `Linkage_Mode` is `'pro-link'` (per `defaultValues()`).
- Each mode has a baseline coordinate placeholder (`LINKAGE_PLACEHOLDER_LINKED`, `LINKAGE_PLACEHOLDER_PROLINK`). `setLinkageMode` auto-swaps placeholders **only if the user hasn't customized values** — `matchesPlaceholder` is the gate. If you change a placeholder, also update the test in `tests/linkage-setup.test.js` if it checks specific values.

### Tests

- `tests/motospec-oracle.test.js` + `tests/fixtures/motospec-oracle.json` is the **cross-solver** harness: 4 bikes × 3 suspension positions of real MotoSPEC v5 output (vendor help-manual screenshots — provenance and the "do not republish to the shared library" rule are in the fixture's own `_provenance` block). Three tiers because the honest answer is not uniform: `static` (topped out) and `working` (≤40 mm fork travel) assert tight tolerances; `deep` (>40 mm) asserts the error stays inside a **recorded envelope** — it pins known divergence rather than pretending to pass, so both a regression AND an improvement will fail it (tighten the envelope when the model improves). Aligning conventions is the whole game here: MotoSPEC's front pot = our `Sag_Front`, but our `Sag_Rear` is vertical wheel travel so it takes their `rear_wheel_travel` OUTPUT, not their rear pot. **This harness caught a real bug**: `Rear_Ride_Height` is ground-referenced (Vertical Pivot-Axle = drop from a *horizontal* line through the pivot), so it must use `Swingarm_Angle`, not the un-pitched angle — 44 mm out at 120 mm of fork travel.
- `tests/validation.test.js` is the reference-bike parity harness. It diffs `computeAll` output against `tests/fixtures/reference-bikes.json` per-bike with a per-bike `tolerance_mm` (default 1 mm). When changing any formula, run the full test suite and inspect this file's output before assuming nothing broke.
- The English-render assertion in `tests/linkage-setup.test.js` deliberately matches `/Rocker Pivot/` (mode-agnostic) because the label differs between linked and pro-link modes.

### Conventions worth preserving

- `src/formulas.js` and `src/linkage.js` are pure; tests rely on this.
- Inline `onclick` handlers are intentional, not legacy — keep the `window` exposure pattern when adding new buttons.
- All units are mm and degrees unless explicitly converted via `D2R` / `R2D`.
- Reference docs live under `docs/` (e.g. `docs/research/linkage-coords.md` for the Melotti-style coordinate description that informs the SVG layout).
