# 3D 扫描 → MotoSPEC 车架数据：手把手操作指南

一次扫描能一次性拿到 app 里最难获取的东西：**10 个连杆坐标**。没有它们，
Motion Ratio、Progression、后轮刚度、Rake/Trail 的载荷响应全都是空的。

> 目标不是做一个漂亮的 CAD 模型，是拿到 **12 个孔的中心坐标**。
> 想清楚这一点，"扫得不够好"的焦虑就没了 —— 不需要完整、光滑、封闭的模型。

## 2. 车怎么准备

### 2.1 能拆就拆 —— 这一条比任何技巧都管用

把避震、连杆、摇臂、发动机拆掉，扫**裸车架**。绝大部分"孔被挡住"的问题直接消失。

拆不掉的孔看 §2.4。

### 2.2 贴标记点（决定成败的一步）

- **视场里任何时刻要能同时看到 ≥4 个点**。车架细长，沿主梁每 **40–60 mm** 贴一个。
- **必须贴得歪七扭八，不能排成直线或规整网格。** 共线的标记点无法解算旋转，
  这是配准漂移的头号原因。
- **不要贴在圆弧边缘、倒角、转角上** —— 要贴在平坦区域，不然中心识别会跳。
- **周围环境也要贴。** 车架架在板子上，板子贴满标记点。扫细节时扫描仪仍有稳定的
  全局参考。**这一步最多人漏，效果最明显。**
- **不要贴在要测的特征上**（轴承孔面、避震座端面），会把数据挖掉。

### 2.3 喷显像剂

阳极氧化黑、抛光铝、镀铬件结构光基本扫不到。喷一层 AESUB Blue，薄而均匀。

### 2.4 挡住的孔怎么办

按优先级：

1. **拆掉** —— 见 §2.1
2. **穿杆法**：找一根精磨圆棒（h6 以上），直径配孔，穿进去两端各伸出 100–150 mm。
   扫外露段（完整圆柱、360° 可见），拟合出的**轴线就是孔的轴线**，精度比直接扫
   短孔高一个数量级。孔中心位置用卡尺量"外露端面→孔中心"的距离补上。
   > **前后轮轴强烈建议用这个方法。** 一个 20 mm 长的轴承孔拟合出的轴向可能差
   > 0.5°，插根长棒能压到 0.02° 级别。
3. **球头适配器**：螺栓拧进隐藏孔，外端粘一颗已知直径的精密钢球。球面拟合精度
   0.02 mm 且**不受覆盖角影响**，只看到 1/3 也能准确定心。
4. **扫 + 卡尺混合**：可见特征之间用扫描，隐藏特征到某个可见基准的距离用卡尺，
   再在脚本里加进去。

## 3. 扫描

Creality Scan 里：

- **对齐模式选 Marker（标记点）**，不要用特征对齐或纹理对齐
- **精度档拉到最高**（点间距最小），文件大不是问题
- **分段扫，每段 20–30 秒就停，单独存。** 一次连扫 5 分钟必然漂移。
  段与段之间靠公共标记点在 CloudCompare 里对齐
- 关掉日光灯、避开阳光直射，别在有窗的白天扫
- 保持在软件提示的最佳工作距离，忽近忽远会引入噪声
- 导出 **.ply**

### 导出：要点云，不要网格

扫描软件里"保存"和"导出"是两回事：

| | 得到什么 | 能用吗 |
|---|---|---|
| **保存 / Save** | 软件自己的**工程文件**（`.crp` 之类，专有格式） | ❌ 只有它自己能开 |
| **导出 / Export** | 通用格式 `.ply` / `.asc` / `.xyz` | ✅ 这才是我们要的 |

导出对话框里如果让你选 **点云(Point Cloud)** 还是 **网格(Mesh)** —— **选点云**。

**为什么不要网格**（实测，平滑 = 网格化的标准步骤）：

| | 半径 | 半径偏差 | 圆心误差 | rms |
|---|---|---|---|---|
| 原始点云 | 13.999 | −0.001 | 0.001 | **0.0382** |
| 平滑 1 轮 | 13.978 | −0.022 | 0.002 | **0.0144** |
| 平滑 4 轮 | 13.959 | −0.041 | 0.006 | 0.0193 |

问题不在精度（圆心误差 0.006mm 其实还行），在于 **rms 掉了 2.6 倍**：

1. **rms 是你唯一的质量哨兵，网格化会让它失灵。** `rms < 0.15mm` 这条红线本来是
   用来抓配准漂移的。平滑之后 rms 永远达标 —— 数据烂着，报告绿着。
2. **补洞会凭空造出不存在的表面**（遮挡区、孔口）。那些点是算法编的。
3. **孔壁和端面之间会生成过渡圆角** —— 真实是一条尖锐的边，而那些虚构的点正好
   落在你最不想要污染的位置。

> ⚠️ 但要分清：**多段扫描的配准/合并是必须做的**（不然 segment 不共享坐标系）。
> 有些软件把配准和网格化都叫"融合"，术语不统一 —— **别看名字，看导出的文件里
> 有没有面片。**

### 拿不准手上的文件是什么？跑这个

```bash
.venv/bin/python inspect_scan_file.py 你的文件.ply
.venv/bin/python inspect_scan_file.py segments/*        # 批量
```

它会告诉你是点云、网格，还是根本没导出（工程文件）。

顺带说明一个容易误会的：**标准 `.ply` 也可以是 binary 编码**，用文本编辑器打开
一样是乱码 —— 但它完全能用，不是加密。这个脚本分得清。

存 `.asc` / `.xyz` 纯文本最保险 —— 那个格式**根本存不了面片**，而且不需要装
open3d。

### 扫完先自检

同一个特征**独立扫两次**，分别拟合圆柱，比轴线夹角和圆心距离。
差 >0.1 mm 或 >0.1° 说明配准还不稳 —— **回去重扫，别往下做**。

## 4. 在 CloudCompare 里切出每个孔

对每个要的特征重复：

1. 拖 `.ply` 进 CloudCompare
2. 左侧选中点云
3. 工具栏 **剪刀图标（Segment）**
4. 鼠标画多边形框住目标特征 → **回车**确认 → 点 **Segment In**（只留框内）
5. 得到一个 `.segmented` 子云 → **File ▸ Save** → 存成单独的 `.ply` 或 `.xyz`
6. 按下面的表命名，全部放进同一个 `segments/` 目录

> 小技巧：先 **Edit ▸ Colors ▸ Height Ramp** 上色，特征边界会清楚很多。
>
> `.xyz` / `.asc` 纯文本也能读，而且**不需要装 open3d**。存不了 ply 就存 xyz。

### 切成什么形状？—— 无所谓，纯度才重要

CloudCompare 的 Segment 是**画多边形沿视线方向拉伸**，所以你切出来的本来就是
"多边形棱柱"，不可能是圆柱。**这没关系** —— 脚本不看你框的形状，只看框里剩下的
点属不属于那个圆柱面（法向量 PCA 定轴 → 圆拟合 → 非线性精修 → 按残差 trimming
迭代剔除离群点）。

也就是说：**不用贴着孔的边缘精细描边。** 粗框就行。真正要控制的是混进来多少
杂点，而杂点分两类，危险程度差一个数量级：

#### A. 分离的杂物（旁边的支架、别的零件）—— 不用怕

配置里默认 `"declustter": true`，会做密度聚类只留最大一簇。实测：

| | 不去杂 | 开 declustter |
|---|---|---|
| 混入旁边零件 15%（距 70mm） | 轴向错 **6.57°**、半径错 40.8mm | **0.003°** ✅ |
| 混入旁边零件 15%（距 40mm） | 轴向错 4.16° | **0.003°** ✅ |

框大了带进旁边的东西，只要它和目标**在空间上分得开**，脚本自己会甩掉。

#### B. 与孔连成一片的表面（孔口倒角、端面、焊缝）—— 这才是要小心的

聚类分不开连续表面，只能靠拟合的 trimming 硬扛。实测（占比 = 杂点/圆柱点）：

| 连续杂点占比 | 轴向误差 | 半径误差 | rms | 判断 |
|---|---|---|---|---|
| 10% | 0.007° | 0.001 mm | 0.038 | ✅ |
| 20% | 0.016° | 0.002 mm | 0.039 | ✅ |
| 35% | 0.074° | 0.008 mm | 0.042 | ⚠️ 接近 0.1° 红线 |
| 50% | **0.408°** | 0.030 mm | 0.081 | ❌ 超标 |

好消息：**rms 会跟着涨**（0.038 → 0.096），所以质量报告能预警。

#### C. 框歪了、左右不对称 —— 完全不影响

最容易有的一个担心：*"我左边少切了一点，剩下的点重心不就往右偏了？拟合出来的
圆心不也跟着偏？"*

对**质心**成立，对**圆心**不成立。实测同一个圆柱切出不同的弧：

| 切到的圆弧 | 点云**质心** | 拟合**圆心**误差 |
|---|---|---|
| 整圈 360° | [−0.45, 0.01] | 0.001 mm |
| 0°–240° | [−2.75, **4.99**] | 0.001 mm |
| 120°–360°（同样长度，位置不同） | [−3.03, **−4.98**] | 0.000 mm |
| 左边少切 20° | [−2.25, 6.37] | 0.000 mm |
| 右边少切 20° | [−4.24, 5.52] | 0.002 mm |
| 只切 90° | [8.97, **8.90**] | 0.003 mm |

**质心到处跑，圆心纹丝不动。** 因为拟合不是在求"点的平均位置"，是在求"到所有点
距离相等的那个点" —— 由点的**曲率**决定，不由点的**分布**决定。原理见文末附录。

所以：框是长方形还是任意多边形、框歪了、偏心了，**都不影响**。框只决定哪些点
留下，而留下的每个点都还老老实实待在真实的圆柱面上。

#### D. 框要**包住**圆，不是内接于圆

一句话：**圆在框里，不是框在圆里。**

点云是**圆柱表面**的点，投影到垂直于轴的平面上就是一圈**圆周**（不是实心圆盘）。
所以框住的是那一圈线：

- 框 ⊃ 圆（把整个圆包进去）→ 整圈 360° 全留下 ✅
- 框 ⊂ 圆（内接，四角碰圆）→ 只剩四个角附近的几小段短弧 ⚠️

但要注意这是个**长方形，两个方向策略相反**：

| 方向 | 怎么框 |
|---|---|
| 垂直于孔轴（圆的直径方向） | **框大**，超过管子外径，把整圈包进去 |
| 平行于孔轴（孔的深度方向） | **框小**，两端各留余量，避开倒角和端面 |

#### 从哪个视角切最好

**从垂直于孔轴的方向看着切**（屏幕上孔呈现为管子的侧面，一个"长方形"）。
这个视角下你能同时控制两个方向：宽度上包住管子，长度上往里收。

**别正对着孔口切**（屏幕上孔呈现为一个圆环）—— 这个视角看不到轴向深度，
你不知道自己框进去多少倒角和端面，而那恰恰是唯一会坑你的东西。

#### 结论：怎么下刀

1. **沿孔的轴向"宁短勿长"** —— 只框孔壁的中间一段，**主动避开两端的倒角和端面**。
   这比"框得完整"重要得多。少切 5mm 孔壁没事，多切进 5mm 端面就开始拉歪轴向。
2. **圆周方向尽量多切**，能框到多少圆弧就框多少（见下面的 §arc 红线）。
3. 旁边分离的东西**懒得框干净也行**，declustter 会处理。
4. 切完看 `quality_report.txt` 的 `rms`：明显高于 0.04–0.05 就是带进了不该带的面。

> 关于圆周覆盖：合成实验里即使只切到 70° 也能拟到 0.016°，但那是**完美圆柱 +
> 0.04mm 噪声**。真实点云有配准漂移和表面缺陷，低覆盖会把这些误差放大，所以
> `arc_span_deg ≥ 120°` 这条红线**照样要守**，别拿合成结果当放行理由。

### 🚨 唯一的硬性要求：所有 segment 必须共享同一个坐标系

切出来的点云**不需要你标任何数值** —— 脚本自己拟合圆柱拿轴线和半径。你只要
切 + 命名。但有一条不能破：

**所有 segment 必须从同一份已配准的点云切出来，切完不要再单独变换任何一个。**

Segment（剪刀）只是删点，不动坐标，所以正常操作自动满足。会破坏它的是这些：

- `Tools ▸ Registration ▸ Align` / ICP —— 会移动点云
- `Edit ▸ Apply Transformation`
- 保存/打开时的 **Global Shift & Scale** 对话框：不同文件选了不同的 shift，
  坐标就错位了。**统一选同一个，或者一律不用**

实测后果（单独把 `rocker_pivot` 绕 Z 转 2° + 平移 3 mm）：

| | 该硬点误差 | 是否报警 |
|---|---|---|
| 扰动**单侧**件（rocker_pivot） | **20.9 mm** | ❌ **零警告，静默错** |
| 扰动**成对**件的一侧（swingarm_pivot_L） | — | ✅ 3 条：左右不共线 1.66°、偏移 14.9 mm、对称面 rms 3.1 mm |

**成对件有左右共线自检兜底，单侧件没有。** 连杆那四个点
（`rocker_pivot` / `rocker_shock` / `rocker_link` / `shock_upper`）全是单侧件 ——
它们错了不会有任何提示，直接进 app 变成错误的 Motion Ratio。切完就别再动。

### 想先把点云摆正再切？—— 可以，而且推荐

上面那条容易被误读成"什么都不能动"。**不是的。** 危险的从来不是"旋转"，是
**让不同 segment 落在不同坐标系里**。判断标准只有两个字：**时机**。

| 做法 | 后果 |
|---|---|
| 切**之前**，对**整个**点云变换一次，另存新文件，之后都从它切 | ✅ 完全安全 |
| 切**之后**，单独动某一个 segment | ❌ 静默错（见上表） |

实测：把全部 16 个 segment 施加**同一个**旋转（31°/−17°/48°）+ 平移 2.5 米 —

| 量 | 原始 | 整体摆正后 | 差 |
|---|---|---|---|
| rake | 24.032° | 24.032° | **0.0000** |
| 轴距 | 1400.300 | 1400.300 | **0.0000** |
| 摇臂角 | 13.499° | 13.499° | **0.0000** |
| offset / trail / 摇臂长 | — | — | **0.0000** |
| **所有连杆硬点、枢轴、轮轴** | — | — | **0.000 mm** |

（唯一"变了"的是 `steering_head`，沿转向轴滑动了几十毫米 —— 那只是拟合返回的
"轴上任意一点"，轴的**方向**没变，所以 rake / offset / trail 全都一样。无害。）

**而且不用摆精确。** 摆正纯粹是为了你眼睛舒服 —— 真正的坐标系是脚本自己重建的
（见下），你手工摆得歪 5° 还是歪 0.5°，结果一模一样。差不多能用 side view 看清
就行，别在这上面较劲。

三种做法，按省事程度排：

1. **扫的时候就摆正**（最省事）—— 车架架在板子上，板子放水平、车身摆正，
   出来的点云本来就大致是正的，后期什么都不用做。
2. **只转视角，不动数据** —— CloudCompare 的切割是在**当前屏幕视角**下画多边形，
   把视角转到合适方向就能切，数据一点没动，零风险。转一次切好几个件。
3. **真的变换数据** —— `Edit ▸ Apply Transformation`，**另存为新文件**，之后所有
   segment 都从这个新文件切。存的时候如果弹 **Global Shift & Scale**，记住选了
   什么，后面所有文件都选同一个。

### 反过来：整车怎么摆**完全没关系**

车歪着扫、斜着扫、扫描仪坐标系乱七八糟，都无所谓 —— 只要所有 segment 是同一个
坐标系。合成验证就是把整车丢进一个**随机刚体变换**再跑，rake 照样还原到 0.002°。

车辆坐标系是脚本自己建的：

| 建什么 | 靠什么 |
|---|---|
| **对称面**（左右中分面） | `symmetry_pairs` 里那几对左右特征 —— **不是**前后轴 |
| **X 轴**（前后方向） | 前后轴连线在对称面内的投影 |
| **+Z 朝上** | `steering_head` 在前轴上方 |
| **把车放平** | 前后轮实际滚动半径之差 |
| **原点** | 后轮触地点 |

所以你不用管车摆得正不正、平不平。你要保证的是 **≥3 对左右成对的件都扫到**
（对称面全靠它们），以及 §5 那三个必填项。

### 要扫哪些件 —— 照这张表来

文件名必须用这些关键词，脚本靠名字认类型和左右。

| 文件名 | 是什么 | 喂给 app 的 | 不扫的后果 |
|---|---|---|---|
| `steering_head.ply` | 转向头轴承孔（上下各扫一段更准） | `Rake_Static`、`Yoke_Offset` | ❌ 全线崩，而且**脚本靠它判断哪边朝上** |
| `axle_front_L/_R.ply` | 前轮轴 | `WB`、`Rf` 基准 | ❌ 建不了坐标系 |
| `axle_rear_L/_R.ply` | 后轮轴 | `WB`、`Swingarm_Length` | ❌ 建不了坐标系 |
| `swingarm_pivot_L/_R.ply` | 摇臂支点 | `beta_static`、**连杆坐标的原点** | ❌ 连杆全废 |
| `footpeg_L/_R.ply` | 脚踏支架 | 只用来定对称面 | ⚠️ 对称面只剩 2 对，精度下降 |
| `rocker_pivot.ply` | 摇杆支点 | `Frame_Rocker_Pivot_X/Y` | ❌ Motion Ratio / Progression 空 |
| `rocker_shock.ply` | 摇杆↔避震 连接点 | `Rocker_To_Shock_X/Y` | ❌ 同上 |
| `rocker_link.ply` | 摇杆↔拉杆 连接点 | `Rocker_To_Drag_X/Y` | ❌ 同上 |
| `link_swingarm.ply` **或** `link_frame.ply` | 拉杆的另一端，**看模式**（见下） | `Drag_To_Swingarm_X/Y` | ❌ 同上 |
| `shock_upper.ply` | 避震上锁点（车架侧） | `Frame_Shock_Top_X/Y` | ❌ 同上 |
| `shock_lower.ply` | 避震下锁点 | 自检用（应与 rocker_shock 重合） | ⚠️ 少一项自检 |
| `countershaft.ply` | 输出轴（前链轮）中心 | `Front_Sprocket_X/Y` | ⚠️ Anti-Squat 空 |

**⚠️ 拉杆那一端扫哪个，取决于你的连杆型式 —— 扫错会得到一个能收敛但完全错误的连杆：**

| 你的车 | 拉杆另一端在 | 存成 | app 里的模式 |
|---|---|---|---|
| 摇杆装在**车架**上（R6、R1、ZX-10R、MT-07…） | 摇臂上 | `link_swingarm.ply` | `linked` |
| 摇杆装在**摇臂**上（Honda Pro-Link、RSV4、老 S1000RR） | 车架上 | `link_frame.ply` | `pro-link` |
| 避震直连、没有摇杆（R3、KTM 890/990 Duke） | 不存在 | 只要 `shock_upper` + `shock_lower` | `linkless` |

分不清就看：**摇杆的转轴螺栓拧在车架上还是摇臂上。**

## 5. 跑脚本

```bash
cd scan

# 1) 扫目录、自动识别类型、自动配对左右，生成配置模板
.venv/bin/python batch_fit.py --init segments/ -o config.json

# 2) 编辑 config.json —— 三处必填，见下

# 3) 跑
.venv/bin/python batch_fit.py --run config.json
```

### config.json 里必须自己填的三处

**① 轮胎半径**（`tyres`）

```json
"tyres": { "front_radius_mm": 304.5, "rear_radius_mm": 320.0 }
```

必须是**实际压载后的滚动半径**：骑上去，量轴心到地面。**不是** 120/70-17 换算的
标称值。差 5 mm，rake 就差 0.2°。

脚本用前后半径差把车的姿态"放平"。这一步很多人漏掉 —— 前后轮半径差 7 mm 在
1375 mm 轴距上就是 **0.29° 的 rake 误差**。

**② 尺度校验**（`scale_check`）—— 别跳过

```json
"scale_check": { "feature_a": "axle_front", "feature_b": "axle_rear",
                 "known_distance_mm": 1375.0 }
```

用卡尺/卷尺实测车架上两个特征之间的真实距离，填进来。结构光扫描的尺度误差是
**系统性**的，不验证的话轴距可能整体偏 0.3%，后面所有 trail 计算全跟着错。

**③ 对称面配对**（`symmetry_pairs`）

至少 3 对左右特征，**且不要共线**。`--init` 会自动配好，检查一下有没有配错。

### 输出（`out/` 目录）

| 文件 | 内容 |
|---|---|
| `quality_report.txt` | **先看这个** |
| `hardpoints_bike.csv` | 车辆坐标系硬点（原点=后轮触地，+X 前，+Z 上） |
| `motospec_inputs.csv` | 参数表，缺的标 MISSING |
| `geometry.json` | 全部结果 + 扫描→车辆坐标的变换矩阵 |
| `hardpoints_scanner.csv` | 原始扫描坐标，便于回 CloudCompare 核对 |

### 质量红线 —— 不达标就回去重扫，别硬算

| 指标 | 门槛 | 不达标的含义 |
|---|---|---|
| `arc_span_deg` | ≥ 120° | 圆周覆盖不够，圆心和半径都不可信 → 换角度补扫或用穿杆 |
| `rms` | < 0.15 mm | 点云噪声或配准漂移 → 喷显像剂 / 加标记点 |
| `n_inliers` | > 500 | 点太少 → 提高扫描分辨率 |
| 左右轴夹角 | < 0.1° | 左右应共线，不共线说明配准漂了 |
| 左右轴偏距 | < 0.2 mm | 同上 |
| 对称面 rms | < 0.3 mm | 某一对左右特征配错，或车架本身歪（撞过？） |

## 6. 转成 app 的字段

```bash
.venv/bin/python motospec_export.py out/geometry.json \
    --name "Triumph 765 (scanned)" \
    --mode linked \
    --fork-position 5 \
    -o out/motospec_catalog.json
```

`--mode` 用 §4 那张表选。`--fork-position` 填扫描当天叉管的伸出量实测值；
不填记 0，表示"**扫描时的状态就是基线**"——差值语义不受影响，以后调叉照样算得对。

它会打印三项自检：

```
trail: 本项目公式 102.92 mm vs 扫描 102.93 mm  差 0.01 mm  ✅
避震眼距: 硬点距离 313.25 mm vs 报告 313.25 mm  差 0.00 mm  ✅
rocker_shock 与 shock_lower 应是同一孔: 相距 0.00 mm  ✅
```

第一项最重要：它用**我们 app 自己的 trail 公式**从 rake/Rf/offset 重算一遍，和扫描
结果对。差 >0.5 mm 就说明 rake、offset 或轮胎半径里有一个不对。

### 扫描给不出、必须另外获取的

| 字段 | 怎么拿 |
|---|---|
| `Mass` / `H_CG` / `L_CG` / 前轮重量分配 | **称重 + 抬轴法** → 用 app 的重心计算器（Chassis Setup 页最下方） |
| `Fork_Stroke` / `Shock_Stroke` | 查规格表，或压到底量 |
| `C_f_aero` / `C_r_aero` | 气动分配，风洞或经验值 |
| 弹簧刚度 / 预载 / 油位 | 拆开量，或看避震铭牌 |

这些留空是**对的** —— 数据表里会显示 `Need: …`，不要拿默认值填进去。

## 8. 出问题查这里

| 症状 | 多半是 |
|---|---|
| 整个坐标系上下颠倒，rake 差一大截 | `steering_head` 扫的位置**不在前轴上方** —— 脚本靠它判断哪边朝上，必须扫真正的头管 |

| `rms` 大 / 表面一层"毛" | 配准漂移 → 标记点太少/共线/贴在了曲面上；或没喷显像剂 |
| `rms` 明显偏高但表面看着没问题 | 切的时候把孔口倒角/端面框进来了 —— 沿轴向往里收，只留孔壁中段 |
| 半径拟出来大得离谱（差几十 mm） | 框进了旁边分离的零件而 `declustter` 是关的 —— 打开它 |
| 左右轴不共线 | 配准漂了，或左右框错了件 |

| 轴距整体偏几个毫米 | 没做 `scale_check`，扫描尺度有系统偏差 |

## 附：拟合是怎么定位圆柱的

想知道"框歪了它凭什么还能算准"，看这里。两步，两步都和框的形状无关。

### 第一步：轴向 —— 靠法向量

圆柱面上**任意一点的法向量都垂直于轴线**。把所有点的法向量收集起来，它们全躺在
一个垂直于轴的平面里 —— 做 SVD，**"没有任何法向量指向"的那个方向**就是轴向。

| 切到的弧 | 轴向误差 |
|---|---|
| 0°–300° | 0.027° |
| 0°–150°（只有一半） | 0.054° |

法向量只跟每个点的**局部朝向**有关，跟它在圆周上待在哪无关。

### 第二步：圆心 —— 是解方程，不是求平均

把点投影到垂直于轴的平面，变成 2D 圆拟合。圆方程展开后**对未知数是线性的**：

```
(u − cu)² + (v − cv)² = r²
        ↓ 展开、移项
[2u, 2v, 1] · [cu, cv, c]ᵀ = u² + v²        其中 c = r² − cu² − cv²
```

每个点给一个方程，未知数只有三个 → **三个点就唯一确定一个圆**：

| 取哪三个点 | 解出的圆心 | 半径 |
|---|---|---|
| 均匀分布 0°/120°/240° | (0.000000, −0.000000) | 14.000000 |
| 全挤在一侧 0°/20°/40° | (0.000000, +0.000000) | 14.000000 |
| 极端偏心 200°/205°/210° | (0.000000, +0.000000) | 14.000000 |

更多的点只是让最小二乘把噪声平均掉，**不是用来"配重"的**。

之后还有非线性精修（最小化真正的几何距离：每点到轴的垂距 − r，5 个自由度），
再按残差把超过 2.5σ 的点剔掉、重拟合，迭代 3 次 —— 这就是少量杂点不致命的原因。

### 切割边缘确实有个小影响

法向量是用 kNN(k=40) + PCA **估计**出来的，切割边界上的点邻域被截断了，估计会偏：

| | 法向量平均误差 | 占总点数 |
|---|---|---|
| 边缘 5° 内的点 | 7.914° | 3.2% |
| 内部的点 | 1.157° | — |

边缘点确实更差，但占比小，而且 trimming 会剔掉离群的。**这也是"弧越长越好"的另一
个理由**：边缘点的占比被稀释了。
